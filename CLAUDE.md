# CLAUDE.md

Project memory for Claude Code. Keep it short and factual, and update it when a decision changes.

## What this repository is

- A fork of Wiki.js (requarks/wiki) that adds an AI assistant to the wiki.
- Work happens on branch `ai-panel`, based on upstream tag `v2.5.315` (the newest tagged 2.x release).
- The installed wiki this will replace runs 2.5.317. Releases 2.5.316 and 2.5.317 are not tagged upstream. They only add a server-side backup feature (`server/core/backup.js`, `server/helpers/zip.js`) and no database migrations. **Decided:** production runs 2.5.315 and that feature is not cherry-picked — `deploy/backup.sh` does the same job, on a schedule, outside the wiki. **Rebase onto `v2.5.317` once upstream tags it** (checked 2026-10-26: still untagged, newest is v2.5.315).
- Upstream's default branch `scarlett` is the Wiki.js 3.0 rewrite. Never base work on it or merge it.

## Goals

1. A slide-in assistant panel inside Wiki.js (done, see below).
2. A RAG knowledge base built from wiki pages, uploaded documents and images, updated whenever a page is saved or a file is uploaded.
3. A chat assistant that answers from the knowledge base, with generative UI cards (done: it answers from the vector index and cites the sections it used).
4. An MCP server so AI agents can search and read the wiki, and file drafts for review (done, step 3c).

## Architecture decisions

- Wiki.js stays the source of truth. Keep edits to upstream files minimal and put new code in new files.
- The AI layer is a separate service in `ai/`, reached on the same origin under `/ai/` through a reverse proxy, so it could serve a different wiki later.
- Assistant panel (done):
  - `client/components/ai/chat-drawer.vue` (panel and launcher) and `client/store/ai.js` (open state, unread count).
  - Included from `client/themes/default/components/page.vue`. The component registers the `ai` store module itself in `beforeCreate`, so `client/store/index.js` is untouched upstream code.
  - Dimensions follow the Landger design: 600px panel, 64px header row aligned with the Wiki.js header, 50px launcher with 14px corners at bottom right. Colours follow the Wiki.js theme, in light and dark mode.
  - **Docks beside the page from 1712px wide**, slides over it below that (Vuetify's `mobile-breakpoint`), full width on phones. That number is `PAGE_MIN_WIDTH + PANEL_WIDTH`: measured at 1280, 1440, 1512, 1728 and 1920 with the page's own nav drawer (256px), table of contents and content beside the panel, the page needs about **1112px** — exactly what it has today on a 1512px screen beside the old 400px panel — before the three columns read properly. Below that the table of contents is cut to five characters ("Befor…", "Resto…") and the content column is narrower than the panel itself. Of the widths tested, 1728 (this Mac) and 1920 dock; 1512 and below slide over. It is measured against the **default** width, not a dragged one, so a drag never changes the mode — with the panel's own width in the sum, the default would sit 16px from flipping on a 1728px screen.
  - **The left edge resizes the panel**, between 400px and half the window, remembered for the browser in `localStorage` (`wiki-ai-panel-width`, a preference, unlike the open state); double-click or Enter resets it to 600. The edge is a focusable `role="separator"` named "Resize the <title> panel", with the arrow keys (16px, 64px with Shift — the separator moves, so in LTR left is wider), Home, End, and Escape to put a drag back. A window too narrow for the stored width clamps what is shown without forgetting it. The pointer is captured, because the drag crosses the iframe and the iframe would otherwise swallow it, and `body.ai-panel-resizing` turns off Vuetify's width animation, blocks the iframe's pointer events and stops text selection. The styles read the live width from `--ai-panel-width` on the body, which is how Wiki.js's floating edit button keeps clear of a dragged panel.
  - The open state persists per browser tab (sessionStorage).
  - Loads the chat app in an iframe from `window.WIKI_AI_PANEL_URL` (set in Admin > Theme > Head HTML Injection), passing query parameters `path`, `locale`, `title` and `theme`. Shows a placeholder when it is unset.
  - What the panel calls itself comes from `window.WIKI_AI_PANEL_TITLE`, set beside the URL in the same injection, defaulting to **Assistant**. It is used in the header, as the iframe's accessible name, and in the launcher and close labels, taken verbatim (no lowercasing, so *iFMIS Helper* survives) and cut at 40 characters.
  - Header buttons, both 32px with 8px corners: **New chat** and **Close**.
  - Messages the chat app may post to the parent window (same origin only; the panel checks origin and source):
    - `{ type: 'wiki-ai:status', label, online }` updates the header status chip
    - `{ type: 'wiki-ai:unread', count }` sets the launcher badge
    - `{ type: 'wiki-ai:close' }` closes the panel
    - `{ type: 'wiki-ai:models', models, selected }` fills the header's model menu
  - Messages the panel posts into the iframe (target origin is the panel's own origin; the chat app takes one only from `window.parent` on a matching origin):
    - `{ type: 'wiki-ai:new-chat' }` cancels a streaming reply, clears the conversation and thread ID from sessionStorage, shows the welcome message again and puts focus in the message box
    - `{ type: 'wiki-ai:set-model', id }` the reader picked a model in the header menu
- Models (decided):
  - **The reader picks the model and the effort from under the message box** (done). `MODELS` in `ai/.env` is the allowlist — `provider:model`, comma separated, menu order, **first entry is the default** — and when set it supersedes the two older settings: `LLM_MODEL` is ignored and `LLM_PROVIDER` is unnecessary, since each entry names its own provider. Only an **explicit** `LLM_PROVIDER=mock` still overrides it (fixed 2026-10-26: the setting's own default is `mock`, and treating an absent one the same way silently ignored a `MODELS` line). Unset, `MODELS` defaults to `anthropic:claude-sonnet-5-5,anthropic:claude-haiku-5-5,ollama:gemma4:e4b` with `LLM_MODEL` moved to the front. `GET /ai/api/models` returns the list with each model's availability (no key / Ollama not running / not pulled), probed and cached 15s. The browser sends only an **id** from that list in `forwardedProps.model`; anything else is refused with `UNKNOWN_MODEL` and logged, so a model the administrator did not list is unreachable. One `ProviderPool` builds a provider per model, lazily, and each run logs the model, the effort and whether the reader chose each. The choice affects answers only — embeddings and image descriptions keep their own settings.
  - **Effort** travels with the run too, in `forwardedProps.effort`, and is validated against *that model's* list: a level it does not offer is refused with `UNKNOWN_EFFORT`. Anthropic's dial is `output_config.effort` (GA, five levels, every current Claude model takes all five; the API's own default is `high` for Sonnet 5.5 and `medium` for Haiku and Opus 5.5, so the service always names it). Ollama has no scale, only thinking, so a local model gets `low` (sends `reasoning_effort: 'none'`) and `high` and nothing between; a model that cannot think would get none and lose the row.
  - **`LLM_EFFORT` sets the default level** — what a reader gets before choosing, and what the menu badges *Recommended*, clamped to what each model has (a local model falls back to its own `high`). **`EFFORTS`** narrows which levels the menu may offer at all, on top of what the model supports; it is enforced by the server, because the route validates against the narrowed list. Unset means every level. `LLM_EFFORT` outside `EFFORTS`, or an unknown name in either, is refused at startup. A model left with nothing keeps no Effort row and runs at its own default.
  - The picker is `ai/panel-ui/src/components/ModelPicker.tsx`, under the message box beside the AI note — **not** in the Vue header, which is back to a plain chip. It opens upwards; a submenu *replaces* the menu's contents with a back control, because the panel is 400px wide and the iframe cannot draw outside itself. Root: the current model with its description and a tick, an "Effort" row showing the level, a "More models" row. Effort submenu: one line on the trade, then the levels, "Recommended" on the default and a tick on the current. More models: the rest, grouped Cloud / On this Mac, unavailable ones `aria-disabled` with the reason. Arrows/Enter/Home/End/Escape (submenu first, then the menu), `menuitem`/`menuitemradio`, light and dark.
  - The effort is remembered **per model** in `localStorage`, because the levels do not mean the same thing across models; the model choice is remembered too, and both fall back to the default if the model leaves the list or cannot answer.
  - The header chip reads "Sonnet 5.5 · Cloud", "gemma4:e4b · Local", "Mock · Dev": "Claude " is dropped because the header has room for about 25 characters at the narrowest the panel goes, and whether the question leaves the Mac is the part worth the space.
  - Effort measured on the three step-3a questions, every level of every model, 42 runs (totals for all three answers; prices from the published table): **Sonnet 5.5** Low 27.3s/$0.0351, Medium 23.6s/$0.0417, High 29.9s/$0.0519, Extra high 34.2s/$0.0608, **Maximum 118.9s/$0.1952 — 5.6× the cost, 4× the time, and the same cards**. **Haiku 5.5** is ~12× cheaper (Low $0.0030 … Max $0.0165) and over-draws below Extra high: four `known_issue` cards on one answer. Low–Extra high all answer correctly on Sonnet; High is where the restore answer gains the troubleshooting table. Medium is the default: the cheapest level that was never thin. Maximum is listed but nothing here showed it earning the money — Haiku at Maximum was *worse*, losing the checklist.
  - **`claude-opus-5-5` is supported but not in the default list** (measured 2026-10-26, 15 runs): from Medium up it draws checklist + table + sources on the restore question — the full set, which Sonnet only reaches at High — but that is the only difference. Sonnet at High gives the same cards for **42% of the cost and 60% of the time** ($0.0519 / 29.9s against Opus Medium's $0.1233 / 49.8s). Opus at Maximum is the worst of all three models' worst: 5.7× the cost, 6× the time, and it *lost* the checklist. Revisit if the wiki grows enough that an answer has to hold several long pages together. Add it by name in `MODELS`.
  - Local models (same sweep): **gemma4:e4b** is listed. At High it matched Sonnet exactly on the restore question (checklist + table + sources), at Low it drew one card across three questions instead of five — which is why thinking stays on — and it returned nothing at all for "error 3201" at both levels. **qwen3.5** is not listed: at High it spent **531s** on one question and drew the same checklist five times, and two of three answers had cards but no text. `OLLAMA_THINKING=0` forces thinking off whatever the reader picked. It is the models, not the plumbing: Ollama's native `/api/chat` and the OpenAI-compatible `/v1` parse a small tool request identically.
  - A run that produces no text and no card now says so instead of leaving an empty bubble; local models sometimes spend a turn thinking and stop.
  - Answers come from a switchable provider, starting with the Anthropic API. Default model `claude-sonnet-5-5`; `claude-haiku-5-5` is the cheaper option. `LLM_PROVIDER=ollama` runs a local model instead — Ollama runs natively on the Mac and containers reach it at `http://host.docker.internal:11434`. `LLM_PROVIDER=mock` keeps the canned replies for UI work and wins over `MODELS`.
  - Production will run on this Mac. The vector index's embeddings are generated locally with Ollama, so only the answering model is a cloud cost.
  - Settings live in `ai/.env` (gitignored, loaded through `env_file`); `ai/.env.example` lists them with no values. The API key is never logged, never returned by a route and never sent to the browser.
- AI service (done, step 3a):
  - `ai/` — Node 22, TypeScript, Fastify, `tsx watch` for development. `ai/panel-ui/` is the chat app (React 19, Vite). `ai/shared/` holds the page context and the answer-component shapes both halves use; it has no dependencies on purpose, because the two are separate npm projects with separate `node_modules`. Versions are pinned and both `package-lock.json` files are committed.
  - The proxy passes the path through, so routes keep the `/ai` prefix: `GET /ai/health` returns `{ ok: true }`, `POST /ai/api/agent` streams one run, `/ai/panel/` is the chat app.
  - Protocol: AG-UI 1.0 over SSE, with the project's own packages — `@ag-ui/client` (`HttpAgent`) in the browser, `@ag-ui/core` and `@ag-ui/encoder` on the server. The page the reader is on travels in `forwardedProps.page`. A card is a tool call: the name has to be one of `sources` (server-built), `checklist`, `known_issue`, `table`, `draft_page` and the arguments have to pass `parsePanelComponent` in `ai/shared/components.ts`, or the panel ignores it.
  - `ai/src/providers/` is one `ChatProvider` interface with two implementations (Anthropic through the official SDK, Ollama through its OpenAI-compatible API). The rest of the agent does not know which is running. `formatAnthropicModel` lives in its own `providers/format.ts` because the configuration builds the picker's labels with it and a provider importing the configuration back would be a cycle.
  - `ai/src/agent/wiki-agent.ts` is the loop: ask the model, run the tools it asked for, ask again, up to `MAX_TOOL_STEPS` rounds; the pass after that offers no wiki tools, so the model has to answer with what it has. The system prompt holds it to wiki content, to the four card components and to citing by source id. Each run logs provider, model, tool calls with timings, and token usage — no page content, no key.
  - Wiki tools (`ai/src/wiki/`) run on the server but always as the reader who asked: the panel is on the wiki's origin, so the browser sends the Wiki.js `jwt` cookie, and the service forwards it as a bearer token. No token means the guest account. `search_wiki` is answered by the index (Wiki.js's `pages.search` is the fallback); `get_page` reads the **rendered** page over HTTP and converts it to Markdown, because `pages.single`/`singleByPath` need `manage:pages` and `Page.content` needs `read:source` — neither is available to an ordinary reader.
  - Admin > Search Engine has to be **Database - PostgreSQL**, not the default Database - Basic: Basic matches titles, descriptions and paths only, so the agent cannot find a page by what is written in it.
  - `ai/src/agent/mock-agent.ts` is still there as `LLM_PROVIDER=mock`: canned answers by keyword, for UI work with no model calls.
  - `dev/containers/docker-compose.ai.yml` adds the service (`ai:4000`), the chat app's Vite dev server (`panel-ui:5173`) and a Caddy proxy on http://127.0.0.1:3080. Only the proxy publishes a port, and the file does not touch `dev/containers/docker-compose.yml`.
  - In development the proxy sends `/ai/panel*` to Vite, hot reload included (its socket runs over port 3080). In production the Fastify service serves `ai/panel-ui/dist` instead.
  - Two settings have to be set by hand in the wiki; `ai/README.md` has them.
- Indexing (done, step 3b):
  - `ai-db` in `dev/containers/docker-compose.ai.yml` is `pgvector/pgvector:0.8.7-pg17` on a named volume, Docker network only. Migrations run at startup from `ai/src/index-db/migrate.ts`: `index_pages`, `index_chunks` (owner — a page or a document, by check constraint — heading path, section anchor, location, text, content hash, embedding, embedding model, generated `fts` tsvector; HNSW index on the vector, GIN on `fts`), `index_documents`, `index_document_links`, `index_queue` (keyed by kind and id, because a page and an asset can share a number), `index_meta`.
  - Embeddings come from Ollama with `EMBED_MODEL` (default `nomic-embed-text`, 768 dims). The width is probed at startup and recorded, because HNSW needs a fixed one. A different model empties the index and rebuilds it; anything wider than pgvector's 2000-dimension HNSW limit is refused rather than half-applied.
  - The queue has one row per page, so repeated saves collapse into one job after `INDEX_DEBOUNCE_SECONDS` (10 in development). A job reads the page through GraphQL with `WIKI_API_KEY`, converts non-Markdown to Markdown, splits at headings into ~300–600 token chunks prefixed with the title and heading path, embeds only chunks whose hash changed, and replaces the page's chunks in one transaction. A chunk never spans a heading: long sections are cut up and short pieces merged, but only within one section, so a chunk's link always matches its text. Unpublished and deleted pages leave the index; a rename only updates the path.
  - Reconciliation runs 5s after startup and every `RECONCILE_MINUTES` (30): it compares Wiki.js's page list with the index, queues what is new or changed, removes what is gone. On an empty index it is the backfill.
  - `/internal/*` deliberately sits outside the `/ai` prefix, so the proxy (which forwards only `/ai/*`) cannot reach it: `wiki-app` calls `http://ai:4000/internal/page-event`, and `http://127.0.0.1:3080/internal/...` lands on Wiki.js instead.
  - `server/modules/storage/rag/` is a new Wiki.js storage module ("AI Assistant Index", key `rag`, push only, `PT30M`). Its page hooks post `{ event, id, path, locale }` and its asset hooks (`assetUploaded`, `assetRenamed`, `assetDeleted`) post `{ event, id, path }`, without awaiting, with a short timeout, logging failures through `WIKI.logger` and never throwing, so a page save never fails or waits. Its scheduled sync calls `/internal/reconcile`, and its admin actions are "Re-index everything" and "Reconcile now". Enable it in Admin > Storage; `ai/README.md` has the steps.
  - Section anchors are Wiki.js's own, read from the rendered page's heading ids (`#troubleshooting`, `#h-1-copy-the-backup-into-the-container`) — the same elements Wiki.js walks to build a page's table of contents, so its slug rules are not repeated here. The `toc` field itself cannot be selected over GraphQL: Wiki.js declares it `String` and resolves it to an array, so the query fails with "String cannot represent value".
  - `WIKI_API_KEY` is the one place an admin token is used, and only the indexer uses it: reading page source needs `read:source`, which no reader has. Questions are still answered with the asking reader's own token.
- Deletions (done): nothing the wiki has stopped showing may be searched, quoted or cited, and nothing derived from it stays in the index.
  - Page deleted, unpublished, moved or a section removed, and file deleted, renamed or replaced: the storage module's event, then the job, which replaces or removes the owner's chunks wholesale. ~11s in development (10s debounce + the job).
  - **Publish window**: a page can be published and still invisible — Wiki.js honours `publishStartDate`/`publishEndDate` and shows an out-of-window page to anyone with *write* permission, so the reader-side check would let an editor or an administrator be cited it. No event fires when a date passes, so the dates are indexed (`index_pages.publish_start`/`publish_end`, migration `011-publish-window`) and used twice: `search.ts` filters them in SQL, so a closed window takes effect on the next question with no indexing at all; reconciliation then empties the page (`emptyPage` keeps the row and blanks `source_hash`, so it knows when to read it again) and re-queues it when the window opens. Pages indexed before the migration are read again once at startup to record their dates — `touchPage` writes the window even when the content is unchanged, because a window can be changed without changing the page.
  - Derived data: `src/indexer/forget.ts` is the one way a page leaves. Chunks, `index_document_links` and `index_image_text` cascade; what does not is the alt text already *copied into* an image's chunks, so every image the page spoke for is queued to be read again. Both the delete job and the reconciliation pass go through it, because a page can leave without an event. `removeDocument` drops the image's AI description in the same transaction, unless another file still has those bytes (the cache is keyed by content hash); the two deletes cannot be one statement, because a data-modifying CTE still sees the row it is deleting.
  - Self-healing at answer time (`src/indexer/stale.ts`): Wiki.js answers 403 for what a reader may not see and 404 for what is not there, so `canReadAsset` is tri-state and `fetchPage`'s 404 is told apart from its 403. A 404 drops the result before the model sees it, queues the page or file to be re-read *by id with the admin key* (so a page that only moved is corrected, not thrown away) and logs it. A cached "yes" would hide that check, so `PermissionCache` keeps a "yes" for 15s and a "no" for 60s, and anything leaving the index clears it.
  - Status: `GET /internal/status` reports the index's counts, the wiki's, the last reconciliation and a `drift.note` of everything out of step, with `inStep`; `?compare=0` skips asking the wiki. Admin > Storage > **Index status** writes the same as one line to the Wiki.js log, because the admin UI only ever says "Action completed."
  - A document whose download 404s is recorded as skipped rather than removed: the same 404 means "deleted" and "Wiki.js will not serve this path", and a removed row would be re-queued by the next reconciliation.
- Model drift (done 2026-10-26): a model's name is not its version, so `index_meta` records which models built the index and a change is acted on at startup. **Embeddings**: Ollama's manifest digest from `/api/tags`, not just `EMBED_MODEL` — a re-pull under the same name empties the index and rebuilds it, the same path a renamed model already took. **Vision**: `IMAGE_DESCRIBER:IMAGE_DESCRIBER_MODEL` (with the digest for a local model) — a change drops the cached descriptions and re-queues the images, and the videos whose frames were described. **Speech**: `STT_MODEL`, *declared* rather than detected, because whisper-server answers `/health` and nothing else — a change re-queues the videos that were transcribed, not the ones that took their words from subtitles. **A fingerprint that cannot be read is never a change**: Ollama being down reports no digest, and an outage must not cost a full re-index. `/internal/status` reports all three under `models`.
- Ollama unavailable (hardened 2026-10-26): **search answers by keyword**, from the index's own GIN half, which needs no model — not from Wiki.js's page-only search, which was the old fallback and could not see files or videos. The tool result carries a note telling the model to say so, and the run logs `source: "index (keyword only)"`. **Indexing waits**: the worker stops claiming jobs so the queue keeps them, a job caught mid-flight is put back *without* spending an attempt (five attempts during an outage used to drop the work), and the retry backs off 2s → 60s with one log line at the start and then one every five minutes instead of one a second. The status says `inStep: false` with the reason. Verified by running the service against a dead port and against a proxy that failed mid-job: attempts stayed 0 and the page was indexed as soon as Ollama came back.
- An image that is only a generated description (done 2026-10-26): a describe call that comes back empty, or a day whose allowance is used up, used to record the picture as having nothing in it — which deleted its chunk and left nothing to ever queue it again. It now keeps what is indexed and tries again next time. Only `empty` and `over-limit` count as transient; `off` and `excluded` are decisions, and the image loses its description as intended.
- Retrieval (done, step 3b): `search_wiki` keeps its name and input schema but is answered by the index. Top 30 chunks by cosine distance (HNSW) and top 30 by full text (`websearch_to_tsquery` + `ts_rank_cd`, GIN), merged with reciprocal rank fusion (`score = Σ 1 / (60 + rank)`), grouped by page, each page keeping its best one or two chunks as a snippet and that chunk's section anchor, so a result links to the section itself (`/en/sops/sqlserver-restore#troubleshooting`). Snippets are tidied for reading: fenced code dropped, table rows flattened, unless that would leave nothing. Wiki.js's own search is the fallback, used only when the index is unreachable or empty, and logged. Because the index is built with the admin key, every candidate page is checked against Wiki.js as the asking reader — the same request `get_page` makes — before anything reaches the model, snippets included; decisions are cached for a minute per reader, keyed by a hash of their token.
- Documents (done): uploaded files are indexed beside pages, so one search ranks both.
  - Scope: PDF, DOCX, XLSX, PPTX, CSV and images (see below). Anything else is recorded in `index_documents` with a status and a reason and logged ("document not indexed"): over `MAX_DOCUMENT_MB` (25, checked from the listing so it is never downloaded), a legacy `.doc`/`.xls`/`.ppt`, an unsupported type, or an image format libvips cannot decode — HEIC ("convert it to JPEG"), SVG, TIFF, BMP, AVIF, icons. Recording the reason also stops reconciliation re-queueing it.
  - A file in a one- or two-character folder (`it/`, `hr/`) is skipped as well: Wiki.js reads the first URL segment as a locale, so the file 404s at its own address — or a same-named file at the root is served instead, under the wrong permissions.
  - `.txt`, `.md` and `.html` uploads are skipped on purpose: Wiki.js's `pageExtensions` makes it serve those URLs as pages, so the file can be neither downloaded nor permission-checked at its own address. `WIKI_PAGE_EXTENSIONS` mirrors the wiki's setting.
  - Extraction keeps the place the text came from, because a citation has to name one: PDF by page (`unpdf`, link `#page=4`), DOCX by heading (`mammoth` then the existing Turndown), PPTX by slide in `p:sldIdLst` order (`fflate` + `fast-xml-parser`; every npm package for this was abandoned, browser-only or numbered slides by file name), XLSX by sheet and row (`read-excel-file`), CSV by row (`csv-parse`). A sheet's header row is repeated in every chunk. Chunking follows the page rules and never crosses from one place in a file into another.
  - The storage module's asset hooks post the id to `/internal/asset-event`; the service lists and downloads the file itself with `WIKI_API_KEY`. Listing walks the folder tree (`assets.list` is per folder and there is no all-assets query), cached ~20s and shared by a burst of uploads. Reconciliation compares that walk with the index by path, size and date.
  - `index_document_links` records which pages link to which file, scanned from each page's rendered HTML as it is indexed; Wiki.js's `pageLinks` holds page-to-page links only. A document source shows "Linked from", filtered to pages the asking reader may open.
  - A document's access is checked as the reader with a `HEAD` of the file's URL, which runs Wiki.js's `read:assets` check; the indexer's download has already warmed the wiki's cache. `get_document` makes the same check.
  - `get_document(path)` is a new tool, in the panel agent and in MCP: it returns the file's text from the index, each part headed with where in the file it came from. `get_page` would fail on a file, so search results carry `kind` and the prompt says which tool to use.
- Videos (done): recordings are searchable like anything else, and a citation points at the minute — "Video · 12:34–14:02", linking to `#t=754`.
  - **They do not live in Wiki.js.** It loads a whole asset into memory on first view, so a recording could not be seeked until it was cached, and `deploy/backup.sh` would carry every video in all fourteen daily dumps. They sit in a folder on the Mac instead — `~/Media/wiki-dev` for development, `~/Media/wiki` for production, both mounted read-only at `/media` (`MEDIA_HOST_DIR` overrides). An unmounted folder switches videos off with a reason in the index status. A video uploaded to the wiki's assets is recorded as skipped, reason "a video; put videos in the media folder".
  - Formats: MP4, MOV, M4V, WebM. **MP4 (H.264) plays everywhere**; Chrome refuses a `.mov` offered as `<source type="video/quicktime">` but plays the same file from a plain `<video src>`.
  - `GET /ai/media/<path>` serves them to **signed-in readers only** (the `users.profile` probe MCP uses, cached a minute) with **range requests**, so the browser can seek to the cited moment. Only videos and the subtitle files beside them are reachable. It is under `/ai/` and not at `/media/` because the proxy already forwards `/ai/*` and nothing else, and because Wiki.js serves assets from the site root, where `/media/` would shadow an asset folder of that name.
  - **A page can embed a player**: Wiki.js's sanitiser keeps `<video>`, `<source>` and `<track>` with their attributes (checked against `html-security`'s DOMPurify configuration).
  - Reading one, all locally, one at a time in the same queue: subtitles beside the file (`.srt`/`.vtt`) or a track inside it, else whisper.cpp; frames at every scene change and at least every `VIDEO_FRAME_SECONDS`, read by Tesseract, each frame keeping only the lines the one before it did not have; then chunks of about `VIDEO_CHUNK_SECONDS` carrying both, each with its start and end. A sentence that straddles a boundary starts the next chunk, so a fact is near the top of the chunk that holds it.
  - Audio goes to whisper.cpp **a window at a time** (~30 s), cut in a silence rather than through a word: bounded memory, and dictation does not queue behind a long recording. whisper's own sentence times place each line, offset by the window's start. **`--no-timestamps` was taken out of the launch agent on 2026-10-26** — it had been set for dictation, which never needed the times, and it was the only reason video citations were approximate. **Do not put it back**: without it the sentence count halves (84 → 43 on a 21-minute recording) and a citation lands wherever a window happened to end — the measured case moved from 14:02, the sentence itself, to 13:33, half a minute into the wrong slide. The fallback is still there and still correct (lines placed inside a window by length); each run logs `timing: whisper` or `timing: window`.
  - Dictation is unaffected by that flag either way: it asks for `response_format=json`, which carries only the text. It does change the *shape* — whisper puts each segment on its own line and with timestamps it finds more segments — so `routes/transcribe.ts` folds the lines into one paragraph after the filler check, which has to run first because it recognises silence by the lines it came back as.
  - `VIDEO_DESCRIBE` is **off by default** — hundreds of frames is a cloud bill. On, it follows `IMAGE_DESCRIBER`, `IMAGE_DESCRIBE_EXCLUDE`, `IMAGE_DESCRIBE_DAILY_LIMIT` and `VIDEO_DESCRIBE_FRAME_CAP` (6, spread evenly). Frame descriptions are cached by the frame's bytes — ffmpeg is byte-deterministic, checked — and `index_video_frames` is what stops the orphan sweep throwing them away (it only knew about documents; a frame's description was being re-bought on every re-index).
  - **No location data, ever**: ffprobe is asked for an explicit field list, everything written out carries `-map_metadata -1`, a frame sent to a model goes through `images/prepare.ts`, and the title comes from the file name, not the container's title tag. Checked with a file carrying GPS, an artist and a comment — none of it reached the index.
  - The folder is watched (events do reach the container through Docker Desktop) *and* swept every `MEDIA_SCAN_SECONDS`; the sweep is what the index depends on. A file must stop changing for `MEDIA_SETTLE_SECONDS` before it is read. Deleting one removes it and its chunks on the next sweep.
  - Schema: `index_videos`, `index_chunks.video_id` + `starts_at`/`ends_at` (the owner check is now `num_nonnulls(page_id, document_id, video_id) = 1`), `index_video_links`, `index_video_frames` — migrations `012-videos` and `013-video-frames`. The locale filter in `search.ts` had to become `o.kind <> 'page'`: a video has no locale, and `kind = 'document'` was hiding every one of them.
  - Measured on an M1 Max, end to end: **about 2 seconds per minute of video** (21 min → 38.9 s; 4 min → 8.2 s), and a third of that when subtitles sit beside the file (3 min → 2.0 s). Timestamps cost about a tenth of the transcription time (24.5 s → 27.1 s on the 21-minute one). Progress — stage and percent — is in `/internal/status` under `media.working`.
- Images and OCR (done): a picture has no text of its own, so three sources are tried and each is a chunk of its own with an `origin` column — `ocr` ("Text in image"), `alt` ("Alt text") and `description` ("AI description").
  - OCR is Tesseract 5 with the English data, installed in `ai/Dockerfile` along with poppler (`tesseract-ocr tesseract-ocr-eng poppler-utils`, ~110 MB, mostly libicu). Flags: `-l eng --oem 1 --psm 3 --dpi 300 -c debug_file=/dev/null`, in that order — any flag written after a config-file name is silently dropped, `--oem 0/2` cannot work (Debian's data is LSTM-only), and `--dpi 300` both helps a screenshot with no resolution metadata and stops Tesseract printing its guess. It always reads a file the service wrote: given bytes it cannot decode, stdin mode treats stdin as a *list of file paths* and OCRs those.
  - The same OCR rescues a scanned PDF: pages are rendered with `pdftoppm -q -png -r 150 -f N -l N -singlefile`, read one at a time, and kept as `Page N` with `#page=N`, so a scan cites like any other PDF. At most 50 pages, logged when truncated; nothing legible leaves it `needs_ocr`.
  - Before an image is sent anywhere, `src/images/prepare.ts` (sharp 0.35.5) decodes it, bakes in the EXIF orientation, resizes and re-encodes it as JPEG — which is what strips EXIF, XMP, IPTC and the colour profile, GPS with them. Only the capture date is read, with `exifr`'s **top-level `pick`**: a per-segment filter (`{ exif: ['DateTimeOriginal'] }`) still returns GPS, and `pick` with `tiff: true` re-enables every segment. The date may be indexed; the position never is.
  - The resize fits both of Anthropic's limits, long edge *and* visual tokens: a long-edge cap alone leaves a 4:3 photo ~50% over the token ceiling and the API silently shrinks it again.
  - `IMAGE_DESCRIBER` (anthropic | ollama | off, default anthropic and off with no key), `IMAGE_DESCRIBER_MODEL` (default `claude-haiku-5-5`, `qwen3.5` for ollama), `IMAGE_DESCRIBE_EXCLUDE` (folders never sent; OCR and alt text still apply) and `IMAGE_DESCRIBE_DAILY_LIMIT` (200). A description is cached in `index_image_descriptions` by the image's **content hash**, so the same picture is never paid for twice, and that table is also the day's tally. Each image logs describer, model, tokens, the size sent and the time taken. Measured: ~1,766 input + ~290 output tokens per image at 1,500–1,570 visual tokens.
  - Ollama's vision models think by default and would spend the whole budget on hidden reasoning, so the describer sends `reasoning_effort: 'none'`; Ollama also needs the `data:` prefix on an image URL and refuses GIF, which is moot because everything is sent as JPEG.
  - Alt text and captions come from the pages that show the image, scanned from the rendered HTML as the page is indexed into `index_image_text`, and an image whose text changed is re-queued. Wiki.js renders `![alt](x)` as a bare `<img>` in a `<p>` and never a `<figure>`; `linebreaks` is on, so a caption written under an image lands in the *same* paragraph after a `<br>`. `>` is not escaped inside an attribute value, so `<img[^>]*>` is the wrong scanner — `src/indexer/page-images.ts` steps over quoted runs instead. An alt that is just the file name (what the asset browser writes) counts as no alt.
  - An image is re-read every time it is queued rather than skipped as unchanged: some of its text comes from outside the file, and re-reading costs only local OCR because the description is cached.
  - A generated description is labelled wherever it appears: "Generated description of this image:" in the indexed text, **AI description** plus a "generated, not read from the image" badge in the card, and the system prompt tells the agent to prefer the text read from the picture when they disagree.
- Creating pages from a draft card (done): the card's **Create page** button creates the page as the logged-in reader, with their own Wiki.js cookie and no admin key in scope, so Wiki.js applies their permissions. A guest sees it disabled, reading "Log in to create pages" (`/ai/health` now returns `signedIn`). The model has no tool for this and nothing in an answer can trigger it: a page appears only because a person pressed the button.
  - `POST /ai/api/pages` (`src/routes/pages.ts`) writes the page unpublished, tagged `ai-draft`, in the Markdown editor, with a `{.is-warning}` note at the top saying it is an unchecked draft and to delete the note before publishing. It is stricter than the read routes because it writes: JSON only (415), the `Origin` must be the wiki's own (403), the reader's token only (401 without one). 409 with `existingUrl` for a duplicate, 400 for a bad path, 503 when the wiki is silent. The log holds a token fingerprint, the id, the path and the timing — never the content.
  - `src/wiki/pages.ts` is the one implementation, shared with MCP's `create_draft_page`; the only difference is that an agent always writes under `drafts/` while a person may choose the path. The duplicated mutation in `src/mcp/tools.ts` is gone.
  - `shared/pages.ts` holds Wiki.js's path rules so both halves check the same ones: no space, dot, backslash or empty folder (`pages.create` refuses them), no unsafe characters (`unsafeCharsRegex`), and no first folder that is one letter, two letters (read as a language code) or in `reservedPaths` (login, img, js, svg, fonts…). Those last ones matter because `pages.create` accepts them and `isReservedPath` is only checked by the editor route, so the page would be created and then be unreachable.
  - The created state lives in `sessionStorage`, keyed by message id and card position (`panel-ui/src/lib/created-pages.ts`), so it survives a reload and the button cannot create twice. It is deliberately **not** in the card's args: those come from the model and are re-validated from storage on load, so a model could otherwise put its own `editUrl` in front of the reader. A stored entry whose links leave this origin is discarded.
- Dictation (done): the composer has a microphone button with a chevron beside it; the chevron opens a popover with a live input-level meter and the microphone list, system default first with a check mark on the one in use, remembered in `localStorage`. Before permission is given the browser hides device names, so the popover says so and offers to ask. Pressing the button again stops, Escape cancels without transcribing, and recording stops by itself at `STT_MAX_SECONDS`. The text is inserted at the cursor and never sent: the reader reviews it and presses Send.

A launch agent at `~/Library/LaunchAgents/vu.gov.doft.whisper-server.plist` starts it at login and restarts it if it exits. Measured on an M1 Max: a 9.8-second clip transcribes in 0.45–0.92 s, a 12.3-second one in 0.56 s.
  - `POST /ai/api/transcribe` takes 16 kHz mono WAV and nothing else — the browser converts the recording with the Web Audio API, so the service needs no ffmpeg and whisper.cpp never transcodes. The RIFF header is parsed rather than trusted: 400 for the wrong shape, 413 over `STT_MAX_SECONDS`, 429 over `STT_RATE_LIMIT_PER_MINUTE` with `Retry-After`, 503 when whisper.cpp is silent. Audio is never stored and never logged; one line per recording holds seconds, bytes, characters and milliseconds.
  - Whisper invents a stock phrase when it hears nothing ("you", "Thank you.", "[BLANK_AUDIO]"), so a transcript that is only filler is treated as nothing heard rather than inserted.
  - `GET /ai/health` carries `speech.enabled`, and the panel shows no microphone when it is false. The service probes whisper.cpp for that answer (cached 30 s), so a half-finished setup never shows a button that cannot work. `STT_PROVIDER=off` hides it outright.
  - **Both local models listen on `127.0.0.1` only, and must stay that way**: neither whisper.cpp nor Ollama has any authentication, so anything that can reach the port can use it. Loopback is enough because Docker Desktop for Mac forwards `host.docker.internal` (192.168.65.254 in the container) to the Mac's loopback — Docker Desktop makes the connection host-side, so it lands on `127.0.0.1`. Verified: the container gets HTTP 200 from both ports while the Mac's LAN address refuses them.
  - **Browsers only allow the microphone in a secure context.** `localhost` and `127.0.0.1` count, which is why dictation works in development over plain HTTP; any other hostname needs HTTPS, so production must be served over TLS or `getUserMedia` will refuse.
  - The panel's iframe already carries `allow='clipboard-write; microphone'` (`client/components/ai/chat-drawer.vue`), so nothing in Wiki.js had to change.

- Citations (done): `ai/src/agent/sources.ts` keeps one registry per run. Every page or file a tool returns is recorded once, with its title (or file name), matching section or place in the file, snippet, date and URL — a file's URL has no locale segment and a PDF's carries `#page=N`, and given a short id (`S1`, `S2`) that the tool result carries. The model writes `[S1]` after the statement it supports and never writes a link or a title; the registry rewrites the markers into `[1](cite:1)` as the text streams (holding back a marker split across deltas, dropping one that names nothing this run returned). The run then ends with a `sources` card the server builds from exactly the cited sources in citation order — or, if nothing was cited but pages were read, from those pages — so an answer drawn from the wiki never ends without sources. Nothing cited and nothing read means no card. In the panel, `panel-ui/src/components/Citation.tsx` resolves `cite:n` against that card (entry *n*), taking the link and title from it, never from the href; a marker whose entry has not arrived yet stays a plain number. `sources` is no longer offered to the model as a tool.
- MCP server (done, step 3c): `POST /ai/mcp` over Streamable HTTP with the official `@modelcontextprotocol/sdk` (1.32.2), stateless — one `McpServer` and one transport per request, each closing over the key that made it. Tools: `search_wiki`, `get_page`, `get_document`, `list_pages`, `create_draft_page`; every result carries the URL, a search hit linking to the matching section or PDF page, so an agent can cite it. Search returns documents as well as pages, marked `kind: "document"` with their location. They reuse the panel's `Retriever`, `WikiClient` and Markdown conversion — no second implementation.

Missing or rejected: 401. Every read runs with that key's own permissions; `list_pages` walks `pages.tree`, which Wiki.js filters itself, rather than `pages.list`, which returns every page regardless.

It must not select `page { locale }` in the response: a freshly created page carries `localeCode`, and selecting the non-nullable `Page.locale` errors after the page has already been written.
- Prompt caching (done): with Anthropic, one `cache_control` breakpoint on the system block (tools render first, so both are cached) plus automatic placement on the last message block, so the growing prefix within a run and across follow-up questions is a cache read. `LLM_PROMPT_CACHE=0` turns it off. Cache read and write tokens are in each run's log line.

- Chat UI (done, on mock data): React and TypeScript in the iframe, streaming AG-UI events. ## Development environment (macOS, Apple Silicon, zsh)

- Everything runs in Docker. Start with:
  `docker compose -f dev/containers/docker-compose.yml -f dev/containers/docker-compose.ai.yml up -d`
  (the second file is the AI service and the proxy; leave it out for the wiki on its own)
- Install dependencies on the first run and after `docker compose down`: `docker exec wiki-app yarn`
- Run the dev server in the background with a readable log:
  `docker exec -d wiki-app sh -c 'yarn dev > /tmp/yarn-dev.log 2>&1'`
- Check the build: `docker exec wiki-app sh -c "grep -nE 'Compiled|ERROR|Failed' /tmp/yarn-dev.log | tail -n 20"`
- Never run `yarn` or `npm install` for Wiki.js on the Mac itself. The same goes for `ai/` and `ai/panel-ui/`: install in the container, e.g. `docker exec wiki-ai npm install --package-lock-only`.
- After changing a `package.json` under `ai/`, rebuild with `--renew-anon-volumes`, or the container keeps the `node_modules` volume from the old image and the new dependency is missing.
- Dev ports: proxy 3080, wiki 3002, Adminer 3001, dev database 15432. The AI service (4000) and the chat app's Vite server (5173) listen inside the Docker network only. Host ports already used by other projects: 3000, 5050, 5435, 5438, 6333-6334, 6379, 8001, 8080, 8088, 8089, 8501, 9000-9001, 54322.
- Open the dev wiki at http://127.0.0.1:3080 (through the proxy), so the wiki and the assistant panel share one origin. Port 3002 reaches Wiki.js directly, without `/ai/`. Use 127.0.0.1, not localhost: this keeps the login separate from the installed wiki at localhost:8088.
- Hot reload cannot swap store modules. After changing anything under `client/store/`, do a full reload (Cmd+Shift+R).
- **`[MASTER] warn: Unable to acquire a connection`, once a minute, is harmless dev noise.** `server/master.js` builds a `connect-session-knex` store, which schedules a session cleanup every 60s and reschedules itself in a `.finally()`, so nothing can stop the chain. Editing anything under `server/` makes `dev/index.js` hot-restart: it calls `WIKI.kernel.shutdown(true)`, which runs `knex.destroy()` (the client sets `pool = undefined`), then re-requires the server *in the same process*. The old store's timer is never cleared, so every 60s it hits the dead client, knex throws, and with no `.catch()` it lands in the `unhandledRejection` handler at `server/core/kernel.js:97`. One orphan per hot restart; the live store still works (the `sessions` table stays pruned). **Workaround: restart the dev server when the log gets noisy** — decided 2026-10-26, no code fix, since `stopDbCleanup()` keys off a static shared handle and would not reach the orphan anyway. **Production is unaffected**: it runs `node server` (`server/index.js`), never `dev/index.js`, and `shutdown()` there ends in `process.exit(0)`.
- Production image: `docker build -f dev/build/Dockerfile -t <tag> .` (use `docker buildx build --platform linux/amd64` for an x86 server). The source reports version 2.0.0 because official builds stamp the real version; handle this when building the production image.

## Branding

- The wiki is branded **GoV iFMIS KB** with the Vanuatu coat of arms.
- `client/static/favicon.ico` and everything in `client/static/favicons/` are regenerated from the crest (`coat-of-arms.png` in the wiki's assets), at upstream's own sizes and formats: ICO with 48/32/16 at 32bpp BMP, PNGs at 16, 32, 180 (apple-touch, flattened onto white because iOS renders transparency black), 192, 256 and 270 (the file called `mstile-150x150.png` is 270px — that is the tile convention), all 8-bit colormap as upstream's are, and `safari-pinned-tab.svg` as a traced monochrome silhouette. `client/static/manifest.json` carries the name. The generator is not kept: the icons are the artefact, and the crest is in the wiki.
- At 16px a detailed crest is unavoidably a smudge; 32px up is clear. A simplified mark for the two smallest sizes is the only way to improve that, and would no longer be the coat of arms.
- **These are upstream files**, the only ones this fork rewrites wholesale rather than adds to. A rebase onto v2.5.317 will show them as conflicts — take ours.

## Conventions

- Small upstream diffs; new code in new files and folders.
- Conventional commit messages (`feat:`, `fix:`, `dev:`, `docs:`) on `ai-panel`. Show me the changes and let me commit.
- Pin dependency versions. No secrets or credentials in the repository.
- **Never print a secret.** No password, API key or token goes into a reply, a report, a commit message, a log line or a file in the repository — not even one you just generated, and not "for convenience". Refer to it by its name (`WIKI_DB_PASS`, `ANTHROPIC_API_KEY`) and say where it lives. Write it with a command that reads it in or generates it in place, so the value never reaches the screen or the shell history.
- After changing client code, confirm the build compiles before reporting the task done.
